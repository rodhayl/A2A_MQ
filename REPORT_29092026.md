# A2A-MQ Final Readiness Report — 2026-09-29

## Executive summary

A2A-MQ is left in a **ready-to-use state for its declared v0.1.0 scope**.

That statement means the repository now has:

- a validated Local-lite runtime that can be installed and started from a fresh Linux checkout;
- a validated optional local Workflow runtime;
- official A2A request, task, streaming and subscription surfaces;
- real Dapr Pub/Sub + JetStream delivery in the local product path;
- durable SQLite task/outbox state locally and shared PostgreSQL support for distributed deployments;
- explicit DLQ, replay, cancellation, ownership and idempotency boundaries;
- a browser Queue Lab for manual inspection/testing;
- a non-mutating `doctor` command for startup/configuration diagnostics;
- a small end-to-end Local-lite smoke command;
- copyable A2A JSON-RPC examples;
- centralized configuration, troubleshooting and distributed-deployment documentation;
- repository checks that detect documentation/configuration drift;
- retained SHA-bound validation evidence for the local, distributed and Kubernetes work;
- immutable RC1/RC2 release-candidate provenance.

`ready to use` does **not** mean third-party certification, a generic exactly-once
guarantee, an HA SLA, a universal RPO/RTO, or that every possible production
infrastructure combination has been certified. Those boundaries remain explicit
throughout the repository.

### 2.3 Local `doctor` preflight

Both local launchers now expose a non-mutating preflight:

```bash
a2amq-local doctor [profile]
a2amq-local-workflow doctor [profile]
```

The preflight checks the things a new user actually needs before startup:

- supported Python;
- installed Python extras;
- profile validity/mode;
- required native binaries;
- pinned Dapr/NATS versions;
- exact native provenance when using the repository bootstrap;
- required startup ports;
- writable local state;
- generated client identity/JWT.

`doctor` intentionally does **not**:

- install software;
- rewrite a profile;
- rotate credentials;
- kill processes;
- auto-repair the machine;
- hide unexpected programming errors.

That keeps the diagnostic path simple and trustworthy.

## 3. Bugs found and fixed during validation

### 3.1 Local doctor JWT read limit

The independent Linux validator found one real usability defect before merging the
onboarding work.

`_read()` used a 512-byte default intended for small local secrets. The generated
RS256 `client.jwt` was larger than that bound, so `doctor` could report a freshly
prepared valid profile as not ready.

The final fix at:

`401471b05da55ba8311b9bc6e5019a24a4250b9b`

made the helper accept an optional limit while preserving the 512-byte default for
ordinary small secrets. Only the generated client JWT path uses the larger bounded
read.

This was a minimal causal fix: no auth bypass, no global bound relaxation and no
change to task/runtime behavior.

### 3.2 Post-merge documentation state

After the usability work had been merged, `README.md` and `docs/STATUS.md` still
contained wording saying the branch was separate from `main` and pending review.

That inconsistency was corrected in a documentation-only post-merge audit.

The original Linux validation report was preserved as historical evidence; a separate
addendum records the repository audit instead of rewriting the original report.

## 5. Native provenance and reproducibility

The local bootstrap does more than check version strings.

The native validation flow binds installed executables to the expected retained
release archives by checking:

- expected platform/architecture;
- expected profile;
- exact archive SHA-256;
- exact archive size;
- expected archive member;
- extracted member size;
- extracted member SHA-256;
- installed executable SHA-256;
- private/bootstrap-owned paths;
- private directory permissions;
- executable version output.

This gives the local runtime a reproducible provenance boundary rather than merely
assuming that a binary named `daprd` or `nats-server` is the correct one.

## 6. Architecture/use model left in place

### Local-lite

The recommended default:

- one Python A2A-MQ process;
- one native `daprd`;
- one native `nats-server` + JetStream;
- SQLite application state;
- no Docker/PostgreSQL/Redis/Placement/Scheduler requirement.

Local-lite intentionally supports immediate deterministic work and the real queue
path. Workflow-only waits/timers/approval semantics fail closed rather than being
reimplemented by a custom local scheduler.

### Local Workflow

Adds:

- native Placement;
- native Scheduler;
- official Dapr Workflow runtime;
- separate Workflow state;
- continuation/approval/timer behavior.

It remains single-host and container-free.

### Distributed / production profile

Supports:

- separate API / Workflow worker / DLQ roles;
- shared PostgreSQL;
- JetStream or RabbitMQ Dapr Pub/Sub profiles;
- MCP;
- optional Vault Transit payload protection;
- telemetry;
- backup/recovery helpers;
- Kubernetes manifest rendering.

Operator-owned production infrastructure remains an explicit boundary.

## 7. Why the project is considered ready to use

The project is considered ready to use because the important paths are no longer
dependent on tribal knowledge or an unfinished validation plan.

### A new local user can:

1. clone the repository;
2. create a Python 3.12+ virtual environment;
3. install `.[local]`;
4. bootstrap exact pinned native tools;
5. run `PASS_NATIVE_VERSION` provenance validation;
6. prepare a profile;
7. run `a2amq-local doctor`;
8. start the runtime;
9. run the small end-to-end smoke;
10. use Queue Lab or the documented A2A JSON-RPC examples.

That workflow has been exercised on real Linux rather than existing only as
documentation.

### A user who needs durable Workflow semantics can:

1. install `.[local,local-workflow]`;
2. bootstrap Placement/Scheduler as part of the pinned local toolset;
3. validate native provenance;
4. prepare the Workflow profile;
5. run Workflow `doctor`;
6. start the five-process runtime.

That path was also exercised on real Linux.

### An operator evaluating distributed deployment can:

- find the configuration contract in one place;
- see which values are secrets;
- see which secret variants are mutually exclusive;
- see the exact storage/Dapr boundaries;
- understand which infrastructure A2A-MQ does and does not provide;
- render digest-pinned Kubernetes application resources;
- use the retained historical live PostgreSQL/broker/Vault/Kubernetes evidence as
  SHA/image-bound reference instead of a vague production claim.

### A maintainer can:

- run static repository checks;
- run focused or complete pytest suites;
- detect docs/configuration drift;
- trace validation evidence to exact SHAs;
- keep RC tags immutable;
- distinguish current documentation from archived historical material.

That combination is why the repository is left as **usable, understandable and
repeatable**, rather than merely feature-complete.

## 8. Known non-blocking boundaries

The following are deliberately **not** treated as blockers for the declared ready
state:

### Hosted GitHub Actions runner availability

Hosted Actions associated with the validated usability work still fail before runner
assignment. The observed jobs have:

- `runner_id=0`;
- empty `runner_name`;
- `steps=[]`.

No repository command executes in those runs, so they are neither code failures nor
positive evidence. Real-Linux validation is the current primary evidence.

### No third-party production certification

The repository continues to state:

- `productionCertified = false`;
- `upstreamBindingCertified = false`.

Repository verdicts such as `PASS_NATIVE_VERSION`, `FULL_PASS` and
`PRODUCTION_DEPLOYMENT_PASS` are project acceptance gates, not third-party
certificates.

### No generic exactly-once claim

Delivery remains at-least-once with explicit idempotency/fencing/outbox boundaries.
Arbitrary external exactly-once side effects are not claimed.

### No universal HA/SLA/RPO/RTO claim

Those properties depend on actual deployed PostgreSQL, broker, Dapr, networking,
backups and operator configuration.

### RabbitMQ Kubernetes parity

RabbitMQ has retained live-broker evidence, but a separate RabbitMQ Kubernetes
deployment parity run has not been recorded.

### Windows native-runtime certification

The repository-pinned native bootstrap/validation path is certified for supported
Linux architectures, not Windows.

None of these boundaries prevents the validated local product from being used or the
implemented distributed profile from being evaluated/deployed under its documented
operator responsibilities.

## 9. What was intentionally not done

To avoid overengineering, the project was **not** expanded with:

- another YAML/configuration layer;
- a custom workflow engine;
- another queue backend abstraction for Local-lite;
- a custom SDK duplicating official A2A;
- an auto-fixing `doctor`;
- a custom process supervisor;
- a GUI installer;
- a documentation framework/generator;
- broad historical document rewrites;
- cosmetic Git history rewriting;
- test assertion weakening;
- global warning suppression;
- release-tag movement.

The final changes favor small diagnosable tools and explicit documentation over new
frameworks.
